# Minimum Profile Unlock Policy v1

Status: ACTIVE

## Goal

Observer Sandbox now prioritizes **vertical completeness before local depth**. The immediate objective is to make every Character Profile section participate meaningfully in the end-to-end simulation workflow with the smallest reliable implementation, then deepen individual systems later.

This policy prevents one profile domain from absorbing the project while foundational simulation systems remain missing.

## Minimum unlock standard

A Character Profile section is **minimum-unlocked** when, where relevant to that section, it has:

1. **Authoritative state** — canonical, simulated, or derived values have a defined owner/source of truth.
2. **Meaningful runtime influence** — at least one real simulation/cognition/action decision can use the section without prose-only mutation authority.
3. **Persistence and presentation** — values remain available across runtime cycles and render through the existing profile/observer surfaces when applicable.

A section does **not** need exhaustive mechanics, a bespoke engine per field, multiple applications, full lifecycle coverage, or deep sub-taxonomies to satisfy minimum unlock.

## Development rule

Use section-sized or structurally equivalent batches whenever the invariant is already proven.

Do not create one PR/deploy cycle per field, Skill application, practice method, or minor profile property unless that item introduces a genuinely new structural invariant.

Default sequence:

`minimum unlock all sections -> verify overall workflow -> deepen highest-value gaps`

## Skill-specific closure rule

For Skills v1, a learned Skill is complete enough for the minimum pass when it has:

- authoritative learned score/grade semantics;
- cognition/profile visibility;
- at least one meaningful represented application where safely runnable;
- a legitimate learning path when practice/training is representable;
- explicit separation between application evidence and learning evidence.

Derived parent Skills do not need direct application or XP. Compatibility fields are not automatically promoted into independent Skills.

The v1 Skill ontology is intentionally shallow. Add child Skills only when a future simulation task requires distinct authority or progression.

## Deferred depth is not failure

The following may remain intentionally deferred after minimum unlock:

- deeper Skill trees;
- multiple task variants per Skill;
- advanced progression/retention/decay;
- relationship-rich or multi-character variants when a second actor is not required for the minimum workflow;
- broad injury, casualty, hazard, treatment, combat, knowledge, economy, job, or quest systems;
- exhaustive personality/preference reward models;
- biography/history simulation beyond relevant cognition/context influence.

## Foundation priority after profile pass

After all Character Profile sections reach minimum unlock, development priority shifts to missing cross-cutting simulation foundations and full workflow continuity rather than immediately deepening any one section.

Examples include:

- profile -> cognition influence;
- generic action/task lifecycle;
- resources/inventory/consequences;
- environment/world context;
- knowledge/familiarity;
- inter-character participation;
- event/lifecycle handling;
- long-horizon progression/decay;
- autonomy planning and goal continuity.

Exact ordering remains evidence-driven and should be chosen after the minimum profile sweep.

## Non-goal

This policy is not permission to fake completeness. A field or section with no authoritative state or no meaningful runtime participation must be classified honestly as not yet unlocked. The purpose is to implement the **smallest real vertical slice**, not to replace missing behavior with documentation claims.
